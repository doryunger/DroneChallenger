# Scene Streaming Readiness

## The problem

Two independent systems need to know "has the world partition cell + Cesium 3D Tiles collision actually streamed in yet," and both were built assuming it either always resolves quickly or doesn't matter:

- `ADroneHUD` gates the loading screen dismissal (and drone input enable, minimap reveal, chase timer start) on `bTilesStreamed`, set by `PollTileStreaming()`.
- `ATargetPawn::TryInitialPlacement`/`PlaceDroneNearCar` run their building-clearance checks (`OverlapAnyTestByChannel`/`LineTraceSingleByChannel` against `ECC_WorldStatic`) on a 1s timer starting at `BeginPlay`, previously on the assumption — stated as a comment, never enforced — that "tiles are loaded here."

If World Partition or Cesium tiles haven't actually streamed collision in yet, both symptoms follow from the same root cause: `PollTileStreaming` checks `UWorldPartitionSubsystem::IsStreamingCompleted()` plus Cesium `Cesium3DTileset::GetLoadProgress()` stability across `RequiredStablePolls` (4 × 0.5s) consecutive polls before declaring `bTilesStreamed = true` — reached via UE reflection (`FindFunction`/`ProcessEvent`) to avoid `#include "Cesium3DTileset.h"`'s Windows min/max macro conflicts. There was no timeout on this: if it never stabilizes (e.g. continuous tile churn near a dense area like Marienplatz that never reads "stable" long enough), the loading screen — and the minimap reveal that lives behind it — hangs forever with no fallback, unlike every other readiness signal in this codebase (`OnMinimapTimeout` at 45s already existed; tile streaming had none). `ADroneHUD::OnTileStreamTimeout` (60s) closes that gap the same way.

Separately, `PlaceDroneNearCar`'s clearance traces ran against this same possibly-unstreamed collision with no gate at all — a trace against a building that hasn't streamed its collision mesh in yet reports "clear" as a false negative, which is how the drone ends up placed inside geometry that renders in moments later.

## The fix

`ATargetPawn::IsSceneStreamingReady()` duplicates `ADroneHUD::PollTileStreaming`'s WP-completion + Cesium-progress-stability check (own state: `PlacementTileProgress`/`PlacementStablePolls`, not shared with `ADroneHUD`'s `LastTileProgress`/`StablePollCount` — these are two different actors with two different timer cadences, 1s here vs 0.5s in the HUD). `TryInitialPlacement` now returns immediately if this isn't true yet, so it keeps retrying every 1s without touching the search logic until collision is trustworthy. This duplication is a known, accepted cost — consolidating both into a shared subsystem/utility would be worth doing if a third consumer of "is the scene actually streamed" shows up.

`PlaceDroneNearCar` also no longer commits to an untested position: previously, if all 20 grid candidates failed `IsClear`, it teleported the drone to `CarPos + 15000cm Z` anyway (never validated) and only logged a `[fallback]` warning. It now returns `bool` — `false` means "don't move the drone," and `TryInitialPlacement` treats that exactly like a failed ground trace: `continue` to the next node candidate instead of committing. The clearance sphere (`SphereR`) also grew from 600cm (6m) to 900cm (9m) for a stricter "too close to a building" margin, and the candidate search now tries left/right of the car (`CarRight`/`-CarRight`) in addition to directly behind, so a blocked "behind" line doesn't waste the whole height tier.

## Confirmed on Vagon: "stable" progress can still be a false-early ready signal

Even with the above fixes, a real crash was confirmed on Vagon: the drone was placed in what read as clear space, then a few seconds later high-detail Cesium tiles streamed in around it and it clipped a building it hadn't collided with a moment earlier. `IsSceneStreamingReady()`'s stability check (`GetLoadProgress()` unchanged for `RequiredPlacementStablePolls` consecutive polls) can plateau once the *currently visible/coarse* tiles for the frustum have loaded, while higher-detail replacement tiles for that same footprint are still being requested and refined — invisible locally where the whole pipeline (coarse then fine) completes inside the polling window, real on Vagon where slower streaming stretches that gap wide enough to place the drone in the middle of it.

Rather than try to predict exactly how long Cesium's refinement takes (unknown, and apparently different across cloud tiers), `IsSceneStreamingReady()` now also requires an extra fixed buffer (`PostStreamingReadyBuffer`, 8s) to have elapsed since the stability check first passed (`StreamingReadySeconds`, reset to 0 whenever stability is lost again) before returning true at all. `RequiredPlacementStablePolls` was also raised from 4 to 6. Neither of these can *guarantee* correctness against an arbitrarily slow refinement — they're both still predictive, just with a bigger margin.

The more robust piece is reactive rather than predictive: `RevalidateDronePlacement`, fired once by a one-shot timer `PostPlacementRecheckDelay` (5s) after `bPlacementDone` is set, re-runs a clearance check (`OverlapAnyTestByChannel`, same `SphereR`) at the drone's *actual current* location — not a candidate location, wherever it really ended up. If geometry has streamed in underneath it since placement, it calls `PlaceDroneNearCar` again to reposition it away from danger. This is the general pattern to reach for when a "wait until ready" signal keeps being falsified by a slower environment: don't just widen the predictive margin further, also check reality again afterward and correct if it turned out to be wrong.
