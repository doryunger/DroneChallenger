# Demo Mode (scripted staging for marketing footage)

## Purpose

A recording-only mode, gated on the `-demo` command-line switch (checked once via `FParse::Param(FCommandLine::Get(), TEXT("demo"))` in `ATargetPawn::BeginPlay()`, cached in `bDemoModeRequested`). Zero effect on any normal launch — there's no way to trigger it without an explicit launch argument, unlike a console variable, which could be toggled at runtime or left on by accident. Built for capturing clean marketing-video footage without requiring live piloting skill: the drone autopilots the chase itself once placed — while still allowing the operator to nudge the drone manually at any time during recording.

To launch with it: add `-demo` to the packaged exe's command line (see `tools/LaunchDemoMode.bat`) or, for Play-In-Editor, add it to the editor's launch/PIE command-line parameters.

## Placement: reuse the normal flow entirely, don't build a parallel one

The first version of this feature gave demo mode its own placement path (`SetupDemoMode()`): a fixed drone spawn at the Marienplatz anchor and a fixed, distant (~756m) car node, followed by a scripted Takeoff-then-Spin climb to close the gap before the chase could even start. That parallel system accumulated a long chain of bugs, each fixed in turn — a car invisible due to stale graph-cached Z, a drone spawning at ~437m from a silent ground-trace fallback, a loading screen hung forever by an unpassable clearance check, Cesium never streaming tiles at the two fixed points because nothing was ever looking at them, and finally a Chase-phase crash caused by an inverted Pitch sign. Even after fixing all of those individually, the drone still overshot its scripted 80m Spin altitude (reported climbing to ~140m) before the yaw-based phase-exit condition fired, then hit Chase with a huge, sudden altitude error — a sharp dive into an uncontrollable spiral. Each fix addressed a real bug, but the underlying design (a bespoke placement and choreography system that normal play never exercises) kept producing new ones.

Replaced entirely: `TryInitialPlacement()` no longer branches into a separate demo path. Demo mode now runs through the *exact same* candidate search, ground-trace, and `PlaceDroneNearCar()` logic normal play has always used and never had placement or visibility bugs in. The only difference is which candidate node gets tried first — demo mode sorts the candidate list by ascending distance from the drone's default (city-center) position instead of shuffling it randomly, so the car reliably lands somewhere recognizable near the Altstadt instead of wherever chance picks. Everything else — the fresh per-attempt ground trace, `PlaceDroneNearCar`'s 15-120m-up / 0-30m-lateral clear-spot search, the car's normal 1500m patrol path, normal (unscaled) `PatrolSpeed`/`EvadeSpeed` — is identical to a human-piloted session. Since the drone now always starts right next to the car exactly like normal play, the Cesium-streaming workaround (manually registered `AdditionalCameras` over two fixed, distant points) is no longer needed and was removed along with it. On top of this placement, a short cinematic intro (climb, spin, correct — see "Sequence" below) still runs before the chase starts, but every target in it is computed relative to wherever the drone actually got placed, not a fixed absolute point.

This also directly addresses the "can't see the car" symptom: the car is placed and grounded with the same proven code path normal play relies on every session, and the drone spawns within the same 0-30m lateral / 15-120m vertical envelope `PlaceDroneNearCar` has always used — there is no longer a separate, distant, custom-geometry placement to go wrong.

## Waiting for the loading screen, not just for terrain

Even with placement fixed, the autopilot could still start steering visibly too early relative to what the player/camera should see. The reason this was never a concern for normal (non-demo) play: normal mode has no autopilot at all, and `ADroneActor`'s player input is only ever enabled once, inside `ADroneHUD::TryDismissLoading()` (`CachedDrone->EnableInput(...)`, disabled at level start) — so even though normal placement also happens early and behind the loading screen, nothing can actually make the drone move until the loading screen (and everything it waits on) has already resolved. There is no equivalent protection for demo mode's autopilot, since it's driven by `ATargetPawn` ticking unconditionally once `bPlacementDone` is true, not by a player controller's enabled/disabled input.

Fixed with a `WaitingToStart` phase between placement and `Chase`. Once normal placement succeeds, if demo mode is active, `TryInitialPlacement()` sets `DemoPhase = EDemoPhase::WaitingToStart` and enables the drone's autopilot — but `TickDemoAutopilot`'s switch has no case for `WaitingToStart`, so it falls to `default: break;`: zero autopilot input, drone just holds via its own calibrated hover throttle, same as sitting idle. Everything placement-adjacent that the loading screen itself depends on (`bPlacementDone`, the `AltStabilityTimer` that eventually fires `OnAltitudeStable`) still happens immediately, exactly as before — only the *visible* autopilot steering is held back. This avoids a real circular dependency: the loading screen's dismissal depends on `ATargetPawn` reaching altitude-stability, which only starts being checked *after* placement succeeds, so placement itself can never be made to wait on the loading screen without deadlocking.

`ADroneHUD::TryDismissLoading()` — the single function that fires once `bAltitudeStable && bMinimapReady && bTilesStreamed` are all true, already the trigger for the BT button's reveal (`BTDisplay->NotifyLoadingDismissed()`) — also calls `ATargetPawn::NotifyLoadingDismissed()`, which transitions `WaitingToStart` straight to `Chase` if the phase is still waiting (a no-op otherwise). `ADroneHUD` holds a `CachedTarget` member for this purpose.

## The car's own driving was fighting the altitude-stability check

`ATargetPawn::CheckAltitudeStability()` samples the car's own `GetActorLocation().Z` every 0.5s and requires 8 consecutive samples (a 4-second window) each within `AltStabilityThresholdCm` (30cm) of the last before broadcasting `OnAltitudeStable` — the one signal `ADroneHUD::TryDismissLoading()` has no independent timeout-free path around (see below). The car starts driving immediately once `bPlacementDone = true`: `Tick()` calls `Tree->tick()` unconditionally, and `target.yaml`'s default (lowest-priority, always-applicable) behavior is `patrol`, which sets a nonzero speed and calls `advance_along_path` every single tick — there is no idle state before movement begins. This is a latent gap in the original design for *any* mode, not demo-specific, though it's more likely to matter wherever the car's very first few seconds of driving cross real elevation change.

Fixed by decoupling "is the ground done settling" from "is the car deliberately driving over real terrain," which is what the check was actually meant to distinguish in the first place: added `bAltitudeConfirmed` (false until stability is confirmed), and `Tree->tick()` — the single thing that makes the car actually move — now only runs once `bAltitudeConfirmed` is true. `CheckAltitudeStability()` sets it alongside its existing `OnAltitudeStable.Broadcast()`. The car now sits genuinely still (Z changing only from residual terrain-snap correction, not deliberate driving) while the stability check runs, so it's measuring what it was designed to measure.

**No timeout fallback for `bAltitudeStable`, deliberately.** A 60-second timeout (`OnAltitudeStableTimeout`, mirroring the sibling `bMinimapReady`/`bTilesStreamed` timeouts) was added at one point, then removed on purpose: forcing the loading screen to dismiss when placement *isn't actually stable yet* would mean the recording starts on top of a genuinely broken or still-settling car/drone — exactly the outcome demo mode exists to prevent. If altitude stability is never reached, the loading screen is now supposed to hang rather than silently proceed with a bad placement — that's the honest signal that something is still wrong, not a bug to be timed around. This makes the fix above load-bearing: with `Tree->tick()` correctly gated behind `bAltitudeConfirmed`, the car sits completely static (it's never physics-simulated — position only ever changes via explicit `SetActorLocation()` calls, and the only other one, `PeriodicTerrainSnap()`, runs on a 60s cadence far outside the 4-second stability window) the moment placement succeeds, so the 8-consecutive-sample check should now pass within a few seconds reliably, on its own, with no timeout needed. `bMinimapReady`/`bTilesStreamed` keep their pre-existing timeouts — those are unrelated, already-proven mechanisms (browser load, tile streaming) that predate this session's work and weren't implicated in any of the placement bugs above.

## Sequence

Driven by `ATargetPawn::TickDemoAutopilot()`, a phase state machine (`EDemoPhase`) ticked once per frame from `Tick()` (mirroring how normal placement gates on `bPlacementDone`):

1. **WaitingToStart** — placement is done, autopilot is enabled, but no input is issued yet (`default: break;`). Holds until the loading screen dismisses.
2. **Climb** — pure vertical throttle, no yaw or pitch, straight up by `DemoClimbHeightCm` (30m) from wherever the drone actually got placed. The target Z is captured once, the moment the loading screen dismisses (`DemoClimbTargetZ = CachedDrone->GetActorLocation().Z + DemoClimbHeightCm`) — *relative* to the drone's real placed position, not an absolute anchor altitude, so there's no way for this to mismatch local terrain elevation the way the old fixed-anchor design could.
3. **Spin** — holds the climbed altitude while pivoting `DemoSpinTotalDeltaDeg` (180°) from whatever heading the drone happened to be facing when Climb finished (`DemoSpinStartYaw`, captured at the Climb→Spin transition) — not tied to a compass direction, so no Cesium ESU conversion needed. Exit condition tracks the drone's *actual measured* yaw delta against the captured start (`FMath::Fmod(CurrentYaw - DemoSpinStartYaw + 720, 360) >= 180`), not a fixed timer, so it reliably completes a genuine 180° regardless of how fast the physics-driven turn actually is.
4. **Correct** — holds altitude, yaws to face the car's actual current position (`ComputeYawErrorToTarget`, shared with `ComputeDemoSteering`), commands zero pitch/no forward motion while doing so. Exists so the drone is already pointed at the car — wherever the car has actually driven to by now — before Chase starts commanding forward pitch, rather than starting Chase from an arbitrary post-Spin heading and relying on `AlignFactor` to taper pitch during the initial turn. Exits once yaw error is under `DemoCorrectYawToleranceDeg` (5°), or immediately if the car is within the 50cm dead zone `ComputeYawErrorToTarget` treats as "no meaningful direction."
5. **Chase** — pursuit with altitude glide (see below) until capture.
6. **Done** — set when `ATargetPawn`'s existing capture logic (`increment_capture_timer` BT action, unchanged) fires; stops the autopilot from continuing to steer once the mission is won.

An earlier version of Climb/Spin targeted a fixed Marienplatz anchor and a compass heading computed via Cesium's `TransformEastSouthUpRotatorToUnreal`, sized to bridge the gap to a fixed, distant car node. That version overshot its altitude target (climbed to ~140m against an 80m target) before the yaw-exit condition fired, then hit Chase with a huge, sudden altitude error — a sharp dive into an uncontrollable spiral. The current version's Climb/Spin targets are relative to wherever placement actually put the drone (right next to the car, same envelope as normal play), so the errors Chase has to correct at the handoff are the same modest size a human pilot would face, not a scripted-choreography-sized mismatch.

## Steering

Chase calls `ComputeDemoSteering(DronePos, TargetXY, TargetZ)`, which produces an `FDroneControlInput` fed into the drone — not a teleport/kinematic move. This matters because `FDroneFlightController::Update` is a real rate/attitude controller (Pitch/Roll command body-relative tilt rate via PID, Throttle is an offset from a calibrated hover value, Yaw commands turn rate) — feeding it synthetic input keeps the same flight physics and visual feel as manual play, rather than looking like a different, disconnected movement mode.

The yaw-error calculation (`ComputeYawErrorToTarget`) is factored out of `ComputeDemoSteering` so the Correct phase can reuse the identical "how far off am I from facing this point" math without also getting Chase's forward-pitch/throttle behavior — Correct wants to yaw in place, not fly forward while doing it.

The steering itself is deliberately simple: yaw toward the target heading (proportional control on yaw error), taper forward pitch during a sharp turn (`AlignFactor`) so it looks like it slows to turn rather than sliding sideways, and a proportional throttle command driven by altitude error. No roll input from the autopilot at all — Roll is left for the pilot's own corrections.

**Bug found: `Input.Pitch = AlignFactor` had the wrong sign.** Per `context/flight-controller.md`'s own documented, empirically-confirmed convention, positive Pitch means "nose up / fly backward," negative means "nose down / fly forward." So exactly when the drone pointed straight at the car (`AlignFactor` near 1), it was commanded to fly backward, away from it — which increases yaw error again, triggers a yaw correction back toward the target, re-triggers the same backward command, and so on, an unstable oscillation that could look like a sharp turn locking into a loop. Fixed by negating the sign: `Input.Pitch = -AlignFactor`.

**The remaining gains (`ThrottleGain`, `YawGain`, altitude/yaw thresholds) are still first-pass estimates reasoned from the flight controller's math, not tuned by actually flying it** — nobody gets autopilot gains right without running them. Expect to adjust `ComputeDemoSteering`'s constants after a test flight (e.g. if it oscillates, lower the gains; if it responds too sluggishly, raise them). With placement now mirroring normal play, the drone starts close enough to the car (0-30m lateral, 15-120m up) that the altitude/yaw errors Chase has to correct at the very start are the same modest range a human pilot would face, not the large, scripted-choreography-sized errors the old Takeoff/Spin design had to correct.

## Manual override

`ADroneActor::SetAutopilotActive(true)` + `SetAutopilotInput(...)` (called every tick from `TickDemoAutopilot`) don't lock out the pilot. In `ADroneActor::Tick`, real player input is read first as normal; then, per axis, if the real input is inside a small deadzone (0.05), the autopilot's value for that axis is used instead. Touch any stick/key and that axis is fully yours until you let go — the autopilot only fills in the axes you're not touching. This is what makes "correcting the drone until it's close enough to capture" possible without fighting the autopilot for control.

## Chase: follow the car's own path, don't freeform-steer at a computed point

The first version of Chase computed a dynamic "intercept point" every second — walking the car's remaining path and comparing ETAs to find where the drone could cut the car off — then freeform-steered at that point with continuously recalculated yaw/pitch. This reproduced the exact same instability class the Takeoff-phase bug had already taught us to avoid: as the drone closed in on the computed point, the direction vector to it shrank toward zero, and `FVector::Rotation()` on a near-zero vector is numerically noisy — except now the "target" was something the drone could actually reach and pass, not just a phase the autopilot skipped past. On top of that, each once-per-second recalculation could jump the target to a different waypoint entirely if the ETA comparison flipped, and the altitude glide was tied to distance-to-*that-point*, so a jumping target meant a jumping altitude command too. Together this produced exactly the reported symptom: a deep dive followed by a swirl right as Chase began.

Replaced with a much more constrained design: the drone follows the *same* waypoint sequence the car is already walking (`CurrentPath`, the identical array `AdvanceAlongGraph()` uses for the car itself), via its own `DemoWaypointIndex` — initialized to the car's own next target (`PathNodeIndex + 1`) the moment Correct hands off to Chase, then advanced one node at a time whenever the drone gets within `DemoWaypointArriveDistCm` (500cm) of its current target node, exactly mirroring the car's own arrival-and-advance pattern (which has never had this kind of instability, because it's the same simple "aim at the next known point, advance on arrival" logic that's been proven stable for the car all along). Since the drone's cruise speed is higher than the car's, it naturally catches up along the shared route without any ETA math at all. `DemoWaypointIndex` is clamped into range every tick, so if the car's path gets regenerated mid-chase (`manage_patrol_path`/`plan_evade_path`, unchanged) and the array shrinks, the index just pins to the new path's last node instead of going out of bounds — a graceful fallback rather than a crash, though in practice the chase should conclude well before the car's own path is ever exhausted.

## Altitude glide

`TickDemoAutopilot`'s Chase case computes a *goal* altitude as `car's current Z + Lerp(DemoChaseLowAltAboveCarCm, DemoChaseHighAltAboveCarCm, GlideT)`, where `GlideT` is the straight-line 2D distance from the drone directly *to the car* (not to a waypoint or computed intercept point) normalized against `DemoChaseGlideStartDistCm` (300m) — 1.0 (high, 80m above the car) far away, sliding down to 0.0 (2.5m above the car) as the drone closes in.

**Bug found: this produced a sudden drop into a dive right as Chase began.** Placement now always starts the drone within 0-30m horizontally of the car (see "Placement" above) — well inside the 300m glide-start distance — so `GlideT` was already near 0 on the very first Chase tick, meaning the *goal* altitude was already "2.5m above the car" from frame one, even though the drone might genuinely be 80-120m above the car at that moment (height and horizontal distance are independent — `PlaceDroneNearCar` can place the drone almost directly overhead). `ComputeDemoSteering`'s throttle is a plain proportional controller with no rate limit of its own (`Clamp(ZError / 800, -1, 1)`) — with a ~100m error, that's an instant, sustained full-throttle-down command, which is the dive-then-swirl the user saw.

Fixed by rate-limiting the *actual commanded* altitude (`DemoCurrentAltAboveCarCm`) separately from the *goal*: it starts at `DemoChaseHighAltAboveCarCm` (80m) the moment Correct hands off to Chase, then moves toward whatever the distance-based goal currently is via `FMath::FInterpConstantTo(..., DemoAltGlideRateCms)` (3 m/s) every tick. This decouples "how fast the drone is allowed to descend" from "how quickly the horizontal gap happens to close" — a full 80m-to-2.5m glide now takes ~26 seconds no matter how close placement started the drone, a genuinely gradual descent instead of a distance-triggered instant drop.

Flying along the same road-centerline waypoints the car uses, while staying relatively high until the last stretch, is also what keeps the drone clear of buildings without needing a separate obstacle-avoidance system: the road graph is inherently building-free at ground level, and the altitude only drops close to street level once the drone is nearly on top of the car, by which point it's following the same clear corridor the car itself is driving through.

## Car-stall watchdog

Since the car is never physics-simulated and only ever moves via the BT's `advance_along_path` calling `SetActorLocation()`, a silent failure anywhere upstream (an empty `CurrentPath`, `Tree` never ticking, `CurrentSpeed` stuck at 0) would leave it sitting motionless with no visible symptom other than the drone chasing a point that never gets closer — easy to misdiagnose as a drone/steering bug instead of a car bug. Added a demo-mode-only watchdog in `ATargetPawn::Tick()`: once `bAltitudeConfirmed` is true (the same gate that starts `Tree->tick()`), every `CarStallCheckInterval` (2s) it compares the car's current position against its position at the last check; if it moved less than `CarStallMinMoveCm` (50cm — the car's actual speed makes several meters of movement per interval the expected case, so this only trips on a genuine stall, not float jitter), `bCarStalled` is set. Exposed via `ATargetPawn::IsCarStalled()` (always `false` outside demo mode). `UDroneTrackingWidget` polls it each tick and, when true, draws a red stroked "CAR NOT MOVING — PLACEMENT ISSUE" line beneath the tracking-time readout — visible in a packaged Shipping build, unlike `AddOnScreenDebugMessage` (stripped in Shipping), matching the pattern the rest of the HUD already uses for on-screen diagnostics.

## Fixed, independently of demo mode: `FDroneGraph::GeneratePath` no longer backtracks

Unrelated to demo mode specifically, but found while building it: `PickNextNode` used to only exclude the *immediately previous* node when choosing the next step, not the full visited set. Hitting a true dead end (a degree-1 node) forced the path to return `CameFrom` — the path would visibly reverse at the dead end and retrace its last step. Rewrote `GeneratePath` as a proper randomized DFS with backtracking: a `TSet<int32> Visited` excludes every node ever added to the path (not just the last one), and hitting a dead end pops the last node off `Path` and keeps searching from the node before it, rather than re-walking into the dead end. The final emitted path a car actually walks never contains a reversal, even though the search itself may explore and discard dead-end branches internally. This applies to *all* path generation, not just demo mode — there was no reason normal gameplay would want visible backtracking either. `PickNextNode` (now unused) was removed.

Verified against the actual road graph (`Content/Graph`, 8,407 nodes): 139 genuine degree-1 dead-end nodes exist, and a fresh path starting exactly on one (all neighbors already visited) used to return a permanent 1-node result — a liveness regression, since the *old* algorithm escaped a dead end by reversing into it, while the rewrite had no equivalent escape. Fixed with a last-resort single step back through `PrevNode` when the search is stuck at the very start. Also found and pruned one disconnected 2-node island (`509`/`6045`, sitting right at the 2km playground boundary — a data-clipping artifact) that neither algorithm could route through sensibly; `Load()` now keeps only the largest connected component. Confirmed via a Python port of the exact algorithm run against the real graph data: 0 stuck results across all dead-ends and 50,000 randomized replan trials after both fixes.

The optional `BiasTarget`/`BiasSteps` params (added for the original anchor-biased demo path, no longer used now that demo mode generates its path the same way normal mode does) default to `nullptr`/`0`, so all call sites keep their original uniform-random behavior.
