# Demo Mode (scripted staging for marketing footage)

## Purpose

A recording-only mode, gated on the `-demo` command-line switch (checked once via `FParse::Param(FCommandLine::Get(), TEXT("demo"))` in `ATargetPawn::BeginPlay()`, cached in `bDemoModeRequested`). Zero effect on any normal launch — there's no way to trigger it without an explicit launch argument, unlike a console variable, which could be toggled at runtime or left on by accident. Built for capturing clean marketing-video footage without requiring live piloting skill: fixed car/drone start positions, a scripted intro flight for the drone, then an autopilot chase that closes on the car — while still allowing the operator to nudge the drone manually at any time during recording.

`bDemoModeRequested` is read once in `ATargetPawn::TryInitialPlacement()`, the same gate that guards normal random placement — if true, `SetupDemoMode()` runs instead of the randomized-candidate search. To launch with it: add `-demo` to the packaged exe's command line (see below for how) or, for Play-In-Editor, add it to the editor's launch/PIE command-line parameters.

## Cesium may never stream tiles at a point nothing is looking at

After the placement and altitude-stability fixes below, the loading screen could *still* hang indefinitely — not because the retry loop was wrong, but because it could be retrying forever waiting for something that was never going to happen on its own. Cesium's tile streaming is driven by registered camera viewpoints (`ACesiumCameraManager`, which by default uses the actual player camera(s) — `UsePlayerCameras = true`) — it prioritizes loading tiles near wherever a camera is actually pointed. The demo car's fixed node is 756m from the anchor, i.e. from wherever the drone (and its camera) actually spawns. If nothing in the scene is ever looking toward that specific point, Cesium has no reason to prioritize streaming collision-capable tiles there, and `GroundSnap`'s line trace at that location could fail *forever*, not just for a while — a genuine, non-timeout-fixable hang, and specific to demo mode's fixed-and-distant car placement (normal mode's random placement always starts its search close to the drone's own position, which the camera is already looking at).

Fixed by registering two additional Cesium cameras (`ACesiumCameraManager::AdditionalCameras`, a manually-populated array independent of the real render camera — exactly what it exists for) in `BeginPlay()`, as soon as the graph loads and demo mode is confirmed active: one 5km directly above the Marienplatz anchor, one 5km above the car's fixed start node, both pointed straight down (`FRotator(-90, 0, 0)`). This forces Cesium to treat both fixed points as being observed from the very start of the level, regardless of where the actual game camera ends up, so their tiles have a genuine reason to stream in before `SetupDemoMode()` ever needs them.

## Fixed placement

`ATargetPawn::SetupDemoMode()` replaces the normal randomized-candidate search entirely when demo mode is on:

- **Drone** spawns at the Marienplatz anchor (48.1374°N, 11.5755°E — the project's own defined anchor point, see `CLAUDE.md`), converted to Unreal space via `CesiumGeoreference->TransformLongitudeLatitudeHeightPositionToUnreal` and ground-snapped by line trace — the same pattern `FDroneGraph::Load` already uses for node coordinates. There's no graph node here on purpose: the graph is a road network for the car, and Marienplatz itself is a pedestrian square, so no road node sits on it.
- **Car** spawns at a fixed graph node (`DemoCarStartNodeId = 26`), chosen empirically from `Graph/nodes.csv`: ~756m due west of the anchor, degree 4 (well-connected, not a near-dead-end). Picked by computing planar distance/bearing from the anchor for all 8,408 nodes and filtering for well-connected nodes in the desired direction — not a guess.

**Bug found in the first pass: the car wasn't visible at all.** `SetupDemoMode()` originally used `Graph.NodeWorldPos.Find(DemoCarStartNodeId)` directly for the car's spawn height. That Z value was baked in once, at `Graph::Load()` time — which runs synchronously and early in `ATargetPawn::BeginPlay()`, almost certainly before Cesium tiles for a location 756m from the anchor had actually streamed in. So the car spawned at whatever fallback height `TransformLongitudeLatitudeHeightPositionToUnreal` produced for a location with no ground yet loaded — buried in geometry or floating far from the visible terrain, either way effectively invisible. The normal (non-demo) random-placement path already re-traces the ground fresh at placement time for exactly this reason (it doesn't trust `Graph.NodeWorldPos`'s baked-in Z either) — `SetupDemoMode()` just hadn't been doing the same.

**Bug found in the second pass, more serious: the drone spawned at ~437m altitude.** The first fix added a ground re-trace (`GroundSnap`), but that helper *silently fell back to the ungrounded position when the trace missed* — it had no way to signal failure, so `SetupDemoMode()` had no way to know the trace hadn't actually found ground, and just committed to placement anyway (`bPlacementDone = true`, timer cleared, never retried). `IsSceneStreamingReady()` already gates `TryInitialPlacement()` before it ever branches into `SetupDemoMode()` — but that check was built around the *normal* placement flow, which always searches within an expanding radius starting very close to the drone's default editor position, so by the time it succeeds, tiles right around that specific (nearby, incrementally-chosen) spot are almost always already loaded. Demo mode instead jumps straight to two *fixed, specific, potentially-distant* points (the anchor, and a node 756m away) — `IsSceneStreamingReady()`'s general heuristic saying "placement is probably fine now" doesn't guarantee collision has actually streamed in at those two particular spots. When the anchor's trace missed, the drone was placed at Cesium's raw "1000m height" reference for that lon/lat — not 1000m above ground, just the ungrounded value the georeference conversion produces before any snapping — which is what produced the ~437m reading.

Fixed by making `GroundSnap` report success/failure (`bool`, mutates the position by reference) instead of always returning *some* position. `SetupDemoMode()` now checks both the anchor's and the car's trace explicitly — if either fails, it logs which one and **returns without committing to placement at all**, leaving `PlacementTimer` running. Since that timer already reschedules `TryInitialPlacement()` (and therefore `SetupDemoMode()`) every second indefinitely — the same retry mechanism the normal random-placement path has always relied on — demo mode now automatically keeps retrying, once a second, for as long as it takes, until both specific locations are verifiably ready.

**Bug found in the third pass, a regression from the second fix: the game hung at the loading screen forever.** Alongside the ground-trace check above, an `IsSpotClearOfGeometry` overlap test (copied from `PlaceDroneNearCar`'s pattern: a 900cm-radius sphere against `ECC_WorldStatic`) was added on the anchor position, intending to guard against the rare case the plaza itself wasn't clear. This was wrong in a way that made it permanently unpassable, not just occasionally strict: `PlaceDroneNearCar` runs that same check on points 15-120m *above* the car — genuinely airborne spots where "is this clear of a building" is a meaningful question. The anchor position, after `GroundSnap`, sits only 50cm *above the ground surface* — and the ground itself is `ECC_WorldStatic` collision. A 9-meter-radius sphere centered half a meter above a surface unavoidably overlaps that surface. The check could never pass, so `SetupDemoMode()` retried forever without ever completing, `bPlacementDone` never became true, `AltStabilityTimer` never started, `OnAltitudeStable` never fired, and `ADroneHUD::TryDismissLoading()`'s three-condition gate (`bAltitudeStable && bMinimapReady && bTilesStreamed`) could never all be true — hanging the loading screen indefinitely, for demo mode specifically (this code path doesn't run at all in normal play). Removed the check entirely; a successful ground trace is the correct and sufficient validation for a ground-level spawn point, which is also exactly what the car's own normal-mode placement already relies on (it doesn't run a separate clearance test on its ground spot either).

**Note on reading the PFD's altitude while debugging this**: `UDronePFDWidget`'s `ALT (m)` tape shows `Drone->GetActorLocation().Z / 100.f` — the drone's raw Unreal Z in meters, not height above local ground, not AMSL in a strict geoid sense, not relative to the car. It happens to read close to true elevation because Cesium's georeference (in "true origin" configurations) keeps raw Z close to height-above-ellipsoid, which is close to real-world elevation. Munich genuinely sits around 500-520m above sea level, so a drone climbing 60-80m above *local* ground can legitimately show 560-600m on this gauge — that's expected, not a placement bug. `SetupDemoMode()`'s success log line records the actual computed anchor ground Z (`drone at Marienplatz anchor Z=...`), which is the number to compare against the PFD reading to tell a real placement error from a units misread.

## Waiting for the loading screen, not just for terrain

Even with placement fixed, the scripted sequence could still start visibly too early relative to what the player/camera should see. The reason this was never a concern for normal (non-demo) play: normal mode has no autopilot at all, and `ADroneActor`'s player input is only ever enabled once, inside `ADroneHUD::TryDismissLoading()` (`CachedDrone->EnableInput(...)`, disabled at level start) — so even though normal placement also happens early and behind the loading screen, nothing can actually make the drone move until the loading screen (and everything it waits on) has already resolved. There is no equivalent protection for demo mode's autopilot, since it's driven by `ATargetPawn` ticking unconditionally once `bPlacementDone` is true, not by a player controller's enabled/disabled input.

Fixed by adding a `WaitingToStart` phase between placement and `Takeoff`. `SetupDemoMode()` now sets `DemoPhase = EDemoPhase::WaitingToStart` instead of jumping straight to `Takeoff` — the drone is positioned, oriented, and `bAutopilotActive` is true, but `TickDemoAutopilot`'s switch has no case for `WaitingToStart`, so it falls to `default: break;`: zero autopilot input, drone just holds via its own calibrated hover throttle, same as sitting idle. Everything placement-adjacent that the loading screen itself depends on (`bPlacementDone`, the `AltStabilityTimer` that eventually fires `OnAltitudeStable`) still happens immediately, exactly as before — only the *visible* scripted flight is held back. This avoids a real circular dependency: the loading screen's dismissal depends on `ATargetPawn` reaching altitude-stability, which only starts being checked *after* placement succeeds, so placement itself can never be made to wait on the loading screen without deadlocking.

`ADroneHUD::TryDismissLoading()` — the single function that fires once `bAltitudeStable && bMinimapReady && bTilesStreamed` are all true, already the trigger for the BT button's reveal (`BTDisplay->NotifyLoadingDismissed()`) — now also calls a new `ATargetPawn::NotifyLoadingDismissed()`, which transitions `WaitingToStart` → `Takeoff` if the phase is still waiting (a no-op otherwise). `ADroneHUD` needed a new `CachedTarget` member to hold onto the `ATargetPawn` reference it already looks up locally in `BeginPlay()` for this purpose.

## The car's own driving was fighting the altitude-stability check — demo-mode specific

`ATargetPawn::CheckAltitudeStability()` samples the car's own `GetActorLocation().Z` every 0.5s and requires 8 consecutive samples (a 4-second window) each within `AltStabilityThresholdCm` (30cm) of the last before broadcasting `OnAltitudeStable` — the one signal `ADroneHUD::TryDismissLoading()` has no independent timeout-free path around (see below). The car starts driving immediately once `bPlacementDone = true`: `Tick()` calls `Tree->tick()` unconditionally, and `target.yaml`'s default (lowest-priority, always-applicable) behavior is `patrol`, which sets a nonzero speed and calls `advance_along_path` every single tick — there is no idle state before movement begins.

In normal mode this rarely causes trouble because the subsequent path is a plain, undirected random walk — over any given 4-second window early on, small elevation changes in different directions tend to at least partially cancel out. Demo mode's path is not undirected: `GeneratePath`'s new `BiasTarget`/`BiasSteps` always greedily picks whichever neighbor is geographically closest to the Marienplatz anchor for the first 15 hops (see below) — a real design choice, requested to make the car "start west, heading into the old city." That greedy bias can easily walk the car down (or up) one consistent street grade for several seconds straight, since Munich's Altstadt does have real elevation — exactly the sustained one-directional Z change that can keep tripping the 30cm/sample threshold and prevent stability from ever being detected during the car's first few seconds of driving, which is precisely the window that matters for how long the loading screen hangs.

Fixed by decoupling "is the ground done settling" from "is the car deliberately driving over real terrain," which is what the check was actually meant to distinguish in the first place: added `bAltitudeConfirmed` (false until stability is confirmed), and `Tree->tick()` — the single thing that makes the car actually move — now only runs once `bAltitudeConfirmed` is true. `CheckAltitudeStability()` sets it alongside its existing `OnAltitudeStable.Broadcast()`. The car now sits genuinely still (Z changing only from residual terrain-snap correction, not deliberate driving) while the stability check runs, so it's measuring what it was designed to measure. This is not demo-mode-gated — it's a latent gap in the original design for *any* mode, just one demo mode's path bias made far more likely to actually manifest.

**No timeout fallback for `bAltitudeStable`, deliberately.** A 60-second timeout (`OnAltitudeStableTimeout`, mirroring the sibling `bMinimapReady`/`bTilesStreamed` timeouts) was added at one point, then removed on purpose: forcing the loading screen to dismiss when placement *isn't actually stable yet* would mean the recording starts on top of a genuinely broken or still-settling car/drone — exactly the outcome demo mode exists to prevent. If altitude stability is never reached, the loading screen is now supposed to hang rather than silently proceed with a bad placement — that's the honest signal that something is still wrong, not a bug to be timed around. This makes the fix above load-bearing: with `Tree->tick()` correctly gated behind `bAltitudeConfirmed`, the car sits completely static (it's never physics-simulated — position only ever changes via explicit `SetActorLocation()` calls, and the only other one, `PeriodicTerrainSnap()`, runs on a 60s cadence far outside the 4-second stability window) the moment placement succeeds, so the 8-consecutive-sample check should now pass within a few seconds reliably, on its own, with no timeout needed. `bMinimapReady`/`bTilesStreamed` keep their pre-existing timeouts — those are unrelated, already-proven mechanisms (browser load, tile streaming) that predate this session's work and weren't implicated in any of the placement bugs above.

## Sequence

Driven by `ATargetPawn::TickDemoAutopilot()`, a phase state machine (`EDemoPhase`) ticked once per frame from `Tick()` (mirroring how normal placement gates on `bPlacementDone`):

1. **Takeoff** — climb straight up from the anchor to `DemoTakeoffAltitudeCm` (60m). Pure vertical: no `ComputeDemoSteering` call at all, throttle only.
2. **Spin** — climb further to `DemoSpinAltitudeCm` (80m) while pivoting clockwise from facing North to facing West, ending exactly where the chase should begin looking. Compass headings are computed via Cesium's `TransformEastSouthUpRotatorToUnreal` (ESU frame: +X=East, +Y=South, so North = ESU yaw 270°, West = ESU yaw 180°) converted at the drone's actual location — not a raw hardcoded Unreal yaw, since that wouldn't reliably correspond to a real compass direction under Cesium's georeference rotation. The turn itself is driven by a constant yaw input (`DemoSpinYawInput`) but the phase-exit condition tracks the drone's *actual measured* `GetActorRotation().Yaw` against the start heading (`FMath::Fmod(CurrentYaw - DemoSpinStartYaw + 720, 360)` compared to the precomputed clockwise delta, ~270°) rather than a fixed timer — so it reliably ends facing the right way regardless of how fast the physics-driven turn actually is, instead of stopping at an arbitrary orientation after N seconds.
3. **Chase** — pursuit with altitude glide (see below) until capture.
4. **Done** — set when `ATargetPawn`'s existing capture logic (`increment_capture_timer` BT action, unchanged) fires; stops the autopilot from continuing to steer once the mission is won.

There used to be a fourth phase, `FlyToStart` (translate ~250m to a point west of the anchor before chasing), removed entirely — the new Spin phase already ends facing the right direction from the same spot, so there's no separate translation leg needed.

## Steering

Chase calls `ComputeDemoSteering(DronePos, TargetXY, TargetZ)`, which produces an `FDroneControlInput` fed into the drone — not a teleport/kinematic move. This matters because `FDroneFlightController::Update` is a real rate/attitude controller (Pitch/Roll command body-relative tilt rate via PID, Throttle is an offset from a calibrated hover value, Yaw commands turn rate) — feeding it synthetic input keeps the same flight physics and visual feel as manual play, rather than looking like a different, disconnected movement mode.

The steering itself is deliberately simple: yaw toward the target heading (proportional control on yaw error), taper forward pitch during a sharp turn (`AlignFactor`) so it looks like it slows to turn rather than sliding sideways, and a proportional throttle command driven by altitude error. No roll input from the autopilot at all — Roll is left for the pilot's own corrections.

**Bug found in the first pass: the drone tilted hard and got stuck mid-turn.** `ComputeDemoSteering` was originally also used during Takeoff, aimed at a purely-vertical target (same X/Y as the drone's own position, only Z differed). That makes `ToTarget2D` a near-zero-length vector — and `FVector::Rotation()` (effectively `atan2`) on a vector that's only nonzero because of tiny physics jitter returns an essentially arbitrary, rapidly-changing angle from frame to frame. The drone was receiving noisy, flip-flopping yaw/pitch commands throughout the climb instead of the intended zero. Fixed by not calling `ComputeDemoSteering` for Takeoff at all — it's pure vertical throttle now, no horizontal steering computed or needed. `ComputeDemoSteering` is only ever called from Chase, where the target is always genuinely far away (never a degenerate near-zero vector).

**The remaining gains (`ThrottleGain`, `YawGain`, `DemoSpinYawInput`, altitude/yaw thresholds) are still first-pass estimates reasoned from the flight controller's math, not tuned by actually flying it** — nobody gets autopilot gains right without running them. Expect to adjust `ComputeDemoSteering`'s constants after the first test flight (e.g. if it oscillates, lower the gains; if it responds too sluggishly, raise them).

**Bug found in the fourth pass: the drone entered a sharp downward turn and crashed right at the start of Chase.** `ComputeDemoSteering` set `Input.Pitch = AlignFactor` — positive whenever the drone was well-aligned with the target. Per `context/flight-controller.md`'s own documented, empirically-confirmed convention, positive Pitch means "nose up / fly backward," negative means "nose down / fly forward." So exactly when the drone pointed straight at the car (`AlignFactor` near 1), it was commanded to fly backward, away from it — which increases yaw error again, triggers a yaw correction back toward the target, re-triggers the same backward command, and so on. Chase is the first phase that ever commands sustained nonzero Pitch (Takeoff is throttle-only, Spin is yaw-plus-throttle-only), which is exactly why the crash only appeared once Chase began. Combined with the throttle/altitude PID and the flight controller's near-inversion recovery logic, this produced exactly the observed symptom — an unstable oscillation that looks like a sharp turn locking into a loop, not a tuning problem. Fixed by negating the sign: `Input.Pitch = -AlignFactor`.

## Manual override

`ADroneActor::SetAutopilotActive(true)` + `SetAutopilotInput(...)` (called every tick from `TickDemoAutopilot`) don't lock out the pilot. In `ADroneActor::Tick`, real player input is read first as normal; then, per axis, if the real input is inside a small deadzone (0.05), the autopilot's value for that axis is used instead. Touch any stick/key and that axis is fully yours until you let go — the autopilot only fills in the axes you're not touching. This is what makes "correcting the drone until it's close enough to capture" possible without fighting the autopilot for control.

## Chase intercept, not tail-chase

`RecalculateDemoIntercept()` (re-run every `DemoInterceptRecalcInterval`, 1s, during the Chase phase) doesn't just steer at the car's current position — it walks the car's remaining `CurrentPath` waypoints, and for each one compares the car's ETA (`distance-along-path / CurrentSpeed`) against the drone's ETA (`straight-line distance / DemoDroneCruiseSpeedCms`, an assumed cruise speed, not measured), picking the first waypoint the drone could reach at or before the car. This is what "since we have the planned path of the car we could already plan where the closest place to catch it would be" means concretely — lead pursuit along a known route, not pure tail-chase. Since the car's path can be regenerated mid-chase (`manage_patrol_path`/`plan_evade_path` BT actions, unchanged, still fire normally), the periodic re-run is what keeps the intercept point current rather than aiming at a route that no longer exists.

## Altitude glide

`TickDemoAutopilot`'s Chase case computes a target altitude as `car's current Z + Lerp(DemoChaseLowAltAboveCarCm, DemoChaseHighAltAboveCarCm, GlideT)`, where `GlideT` is 2D distance-to-intercept normalized against `DemoChaseGlideStartDistCm` (300m) — 1.0 (high, 80m above the car, matching the altitude the Spin phase just finished at, for continuity) far away, sliding down to 0.0 (2.5m above the car) as the drone closes in, so it's naturally near capture altitude by the time it's actually close. This is a direct implementation of "keep the drone around 60-80m and then slowly close down on the car as it's getting closer."

## Car speed and path shape

`PatrolSpeed`/`EvadeSpeed` are scaled by `DemoCarSpeedScale` (0.5×) at runtime in `SetupDemoMode()` only — the Blueprint/asset defaults aren't touched, this only affects the live instance when demo mode is active. Slower car = more margin for the drone to close the (deliberately large) initial gap, per the explicit tradeoff requested.

The car's initial path is generated at `DemoCarPathDistanceCm` (5km) instead of the normal 1500m, with the first `DemoCarPathBiasSteps` (15) hops greedily biased toward the Marienplatz anchor (`GeneratePath`'s new optional `BiasTarget`/`BiasSteps` params — see below) — "start west heading into the old city, then go anywhere."

## Car-stall watchdog

Since the car is never physics-simulated and only ever moves via the BT's `advance_along_path` calling `SetActorLocation()`, a silent failure anywhere upstream (an empty `CurrentPath`, `Tree` never ticking, `CurrentSpeed` stuck at 0) would leave it sitting motionless with no visible symptom other than the drone chasing a point that never gets closer — easy to misdiagnose as a drone/steering bug instead of a car bug. Added a demo-mode-only watchdog in `ATargetPawn::Tick()`: once `bAltitudeConfirmed` is true (the same gate that starts `Tree->tick()`), every `CarStallCheckInterval` (2s) it compares the car's current position against its position at the last check; if it moved less than `CarStallMinMoveCm` (50cm — the car's actual speed makes several meters of movement per interval the expected case, so this only trips on a genuine stall, not float jitter), `bCarStalled` is set. Exposed via `ATargetPawn::IsCarStalled()` (always `false` outside demo mode). `UDroneTrackingWidget` polls it each tick and, when true, draws a red stroked "CAR NOT MOVING — PLACEMENT ISSUE" line beneath the tracking-time readout — visible in a packaged Shipping build, unlike `AddOnScreenDebugMessage` (stripped in Shipping), matching the pattern the rest of the HUD already uses for on-screen diagnostics.

## Fixed, independently of demo mode: `FDroneGraph::GeneratePath` no longer backtracks

Unrelated to demo mode specifically, but found while building it: `PickNextNode` used to only exclude the *immediately previous* node when choosing the next step, not the full visited set. Hitting a true dead end (a degree-1 node) forced the path to return `CameFrom` — the path would visibly reverse at the dead end and retrace its last step. Rewrote `GeneratePath` as a proper randomized DFS with backtracking: a `TSet<int32> Visited` excludes every node ever added to the path (not just the last one), and hitting a dead end pops the last node off `Path` and keeps searching from the node before it, rather than re-walking into the dead end. The final emitted path a car actually walks never contains a reversal, even though the search itself may explore and discard dead-end branches internally. This applies to *all* path generation, not just demo mode — there was no reason normal gameplay would want visible backtracking either. `PickNextNode` (now unused) was removed.

The optional `BiasTarget`/`BiasSteps` params default to `nullptr`/`0`, so both existing call sites (`manage_patrol_path`'s 1500m replan, `plan_evade_path`'s 500m evade segment) are unaffected and keep their original uniform-random behavior.
